# TyporaCode Collaboration Rules

<a id="section_cb0085fa4f10"></a>
## Project Boundaries

TyporaCode is an independently maintained Typora workbench enhancement project. All implementations, builds, test cases, run instructions, and development handovers are maintained in this repository. Before entering the repository, read this file, [README](README.md), [Enhancement Module Description](enhancements/README.en.md), and [Development Handover](docs/development_handoff.en.md).

This project does not depend on the original knowledge base's directory structure, AGENTS, root scripts, or local absolute paths. Do not return to the original repository for development, maintain duplicate code, or add cross-repository synchronization processes. Upstream research cache belongs to the `.cache/` ignored by this repository and does not constitute a runtime dependency.

## Modification Discipline

- User requirement ledger is stored in the Git-ignored `.cache/issue_tracking/requirements.md`. Before starting work, read the ledger; for each new feedback, first append a number, original intent, acceptance conditions, and status, then implement. Subsequent messages default to supplementing existing tasks and cannot overwrite unfinished items; repeated feedback is merged into the original number and retains the reproduction date.
- Completed items must include verification evidence from this round and commit/install status; items not verified cannot be marked as completed. During wrap-up, verify each item from this round and previous unfinished items; for unresolved items, state the reason and next steps. If the ledger is lost, rebuild it from the current conversation and `docs/feedback_review.md`; do not treat historical pass records as the results of this review.

- 2026-09-29 R082: Comments in proprietary code must be in English, preserving meaning and third-party original statements; this agreement replaces the previous requirement for comments to be in Chinese. Release notes and usage/development documentation provide separate Chinese and English pages, not mixed in the same document; Chinese design and handover documents still use clear Chinese, first explaining actual behavior, trigger conditions, and verification results. The full scope and migration status can be found in [Chinese and English Release Design](docs/localization.en.md).
- Files, directories, types, functions, variables, and interface fields in proprietary code must be in English `snake_case`; constants are allowed `UPPER_SNAKE_CASE`. Interface names enforced by language, system, and third-party sources retain their upstream forms, without expanding exceptions.
- Before editing, check `git status --short` and related diffs to protect existing uncommitted content. Do not overwrite, clear, cancel staging, or commit user-irrelevant changes.
- Refactor using the current target architecture after clarifying the actual call relationships; do not arbitrarily add old interface forwarding, dual runtime, dual writes, or deprecated path aliases.
- All features comply with the principle of role layering: UI independently organizes presentation, shared business operations are performed through command/service calls; the same business state and configuration are managed by only one place, native capabilities are centrally adapted, and events and resources are uniformly cleaned up by their owners. This rule applies to files, search, outline, Git, terminal, and window management, not limited to the Explorer. Abstractions are based on real shared responsibilities, no purposeless general frameworks are created, and independent domains are not forced into a single large module.
- Documents and scripts explicitly use UTF-8 for reading and writing; long-term documents should not include personal directories, drive letters, shared addresses, credentials, or tokens.
- UI modifications must check the geometry, theme state, and keyboard interactions of similar panels; it is not acceptable to claim complete acceptance based on partial screenshots or old test passes. When repeated offsets occur in the same layout area, such as the status bar, first fix the common layout contract and perform regression testing on all similar controls; new status bar controls must reuse shared groups, operation, and text roles, and should not add margin/top compensation separately in each module. Native state classes cannot be directly spread to independent menus; verification must cover actual text line boxes, icons, and non-hover visibility, not just compare outer rectangles.
- Ordinary controls use the default interaction of the public factory. Views register semantic control scope via `acquire_workspace_interaction(root)`, and dynamically added buttons are automatically integrated. The unified layer manages hover colors, default 4px control corner radius, and keyboard focus. Each UI retains its own dimensions, selected/expanded, and disabled states. Independent shapes such as circles and split buttons are declared via `--workspace-interaction-radius` and cannot be overridden by local right-angle defaults shared rules. Independent differences are declared via roles, CSS variables, or explicit `none` boundaries; do not copy another set of hover rules for ordinary buttons. Document content and third-party editors are not included in global repaints.
- Information popups reuse common appearance and reusable delay, boundary, focus, and cleanup mechanisms. The domain only owns content and asynchronous data; use local options when different delays are needed. Tabs and status bars share content centering rules, but each has its own area height. New UI must verify dynamic addition, local override, disabled/selected priority, and destruction recovery; complete contract see [Workbench Interaction Design](docs/workspace_interaction.en.md).
- Scrollbar base width, corner radius, and native three-state colors are unified via `workspace_scrollbars.css`. Monaco/xterm/reading thumbnails only centrally adapt the slider shape, while scrolling and theme states remain with the original owner. New panels must not copy base rules, retain hidden scrollbars and verify real rendering; task progress and scrollbars are verified separately by semantics.
- The workbench loads static styles and persistent scripts directly when starting Typora, does not register community plugins, and does not rebuild the workbench when opening files or switching folders. When modifying the startup process, verify first render, single initialization, listeners and DOM cleanup, unsaved documents, and consistency with the runtime entry.
- 2026-09-20 User reauthorization for community plugin capability access: First ensure existing TyporaCode UI startup and interaction, layout remains unchanged; community APIs are accessed via an adapter layer on the same workbench, without restoring a second set of community core or UI. Native naming follows snake_case, third-party ABI compatibility is enforced. After official Typora updates, re-execute standard installation, native startup icon remains unchanged; see community plugin and startup design. This agreement overrides previous restrictions that prohibited community plugin access.
- Do not arbitrarily delete user files or notes; when operations may affect user data, environment, or irreversible actions, first specify the exact scope.

## Requirement and design document management

- **Each requirement must have a corresponding requirement design document or precisely locatable design section, and must be continuously maintained.** This requirement applies to all features, including defect fixes, performance optimizations, UI, configuration, architecture, documentation, and delivery rules, not limited to files or terminals.
- New feedback first registers stable requirement number, source date, original intent, and acceptance conditions, then links to authoritative design sections in [Requirement Design Index](docs/requirements_design.en.md#section_289804dcfb33). Design documents are placed in version control within `docs/` or existing corresponding feature documents; session ledgers and temporary evidence continue to be placed in Git-ignored `.cache/issue_tracking/`, cannot replace formal design with temporary ledgers.
- Design must at least explain the problem and goal, scope and what is not included, interaction and failure/cancel behavior, module responsibilities and state owners, implementation plan and important trade-offs, acceptance and regression methods. Trim according to requirement scale; small fixes can update the original design section. Related requirements can share the same authoritative document, cannot consider each feedback as design completion by copying a design or only pasting a file link.
- Before implementation, supplement the design; when requirement clarification, scope changes, and implementation adjustments occur, update the corresponding design, index, and ledger, noting the date, reason, and replaced agreement. Subsequent messages cannot overwrite other unfinished items. When facts are missing, mark as pending design or pending verification, retain unresolved issues, and do not fabricate host interfaces or acceptance results out of nowhere.
- Finalize the step-by-step verification of 'Requirement → Design → Implementation → Verification → Delivery'. Track design coverage and implementation progress separately; only when design, partial implementation, or old verification is present, the requirement cannot be marked as completed. When migrating, renaming, or splitting design documents, maintain all requirement links synchronously, and keep the unimplemented parts as independent sub-items.
- Formal index manages numbering and design entry points, domain documents manage design content, local ledger manages progress and current evidence, [feedback records](docs/feedback_review.en.md) manage delivery history; do not maintain multiple independent completion lists. When the ledger is missing, first recover the numbering and document associations from the formal index, then verify the conversation and delivery records to restore the status.
