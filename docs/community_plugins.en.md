Continue starting existing workbench with native Typora icon. Load user-enabled extensions after workbench initialization is complete; plugins cannot be prerequisite dependencies for base interface startup. Public core API exposes the same core instance through upstream v2 Symbol, only extension ABI access, no second community core, built-in plugins, or workspaces run. Plugin service is the sole owner of list, enabled status, instance, installation location, and operation queue. Folder switch does not automatically scan and run plugins in repository, uniformly uses dedicated plugin directory under user data; does not restore private knowledge base paths or per-repository plugin override rules. Each window has its own instance, disk installation uses mutual exclusion and transactions; configuration and plugin program are separated, uninstall retains settings and clearly provides feedback.

## API and implementation

Restore Plugin, PluginSettings, configuration components, and commonly used public exports from the fixed community source code, retaining upstream licenses and source summaries. Enforce class names, lifecycles, and Symbols from the upstream; new services, fields, and functions use snake_case. Register Plugin commands, events, scripts, styles, and settings pages to existing lifecycles, and clean up already registered resources on abnormal initialization; a single plugin failure does not prevent other plugins and the base workbench.

The management UI is separate from the service. The community catalog and packages come from explicitly identified upstream repositories and pinned release identities; network requests have timeout and size limits. Manifest validation checks the id, version, minimum core version, platform, and paths. Installation and updates prepare and validate the complete candidate before switching the target directory, retaining the previous package on failure. They do not uninstall the old plugin before downloading. Local packages undergo the same checks. Invalid paths, ZIP entries, symbolic links, or manifests prevent code execution.

Whether a plugin is enabled is managed only by its dedicated configuration; scanning does not enable new plugins. Enable/disable/update operations are serial, and repeated clicks are idempotent; loading stale, disabled, or destroyed plugins does not reactivate them. Plugin CSS only exists during enablement. After updating a running plugin, a manual normal restart is required for changes to take effect, avoiding multiple windows still executing deleted modules; user windows are not automatically closed.

Native preference commands still open Typora preference settings; the gear in the lower left corner, per R072.1, only provides unified settings and extensions; native preferences/community settings are directly accessible via the settings category area. Core upgrades of the community framework itself do not allow overriding this project's core; the workbench itself continues to update via R047. Official Typora upgrades re-run the standard installer per R056's latest confirmation method, without adding a launcher or automatic repair service.

## Acceptance and Boundaries

Unit-level verification of checklists/path/version, serial start/stop, failure rollback, and resource cleanup; 20/100/1000 tiers cover repeated operations and stale results; function-level verification of menus, search, busy/error/cancel, settings registration, focus, themes, and switch states; system-level verification installs and runs a fixed version of real community plugins on an original Typora independent copy, checking command effects, disable cleanup, workbench single instance, and draft retention. Network and ZIP stand-ins and real upstream downloads are separately recorded and cannot be mixed as online acceptance.

Record API coverage and plugin instances item by item; the minimum version passing does not equate to compatibility with all third-party plugins. Plugins that depend on unopened community internal services, another plugin framework, or unknown native interfaces explicitly fail, without using empty functions to fake success. Actual changes, checks, installations, and native acceptance results are archived under a unified evidence system; current verification and installation status is seen in feedback records and test evidence, not treating API export count as all plugin compatibility.

## Implementation Contract (2026-09-20)

The initial entry is the Help menu's 'Community Plugin...'; on 2026-09-20, the entry agreement below R060 replaces it. The management page supports searching for installed/community directories, selecting ZIP system files, trusting and enabling, disabling, settings, checking and updating, and uninstalling. Installation defaults to disabled; switching or hiding the sidebar retains the management view and unique subscription, and ongoing authorized installation transactions continue; on destruction, interface subscriptions are released. During workbench destruction, network operations are stopped and instances are cleaned up.

The program saves package content summaries in community/packages/id/revision under user data, and plugins.json only atomically publishes selected versions and enable status. Updates retain the currently used old directory, and each window maintains its own loaded version and displays a wait for restart; disable/uninstall operations are passed to other windows via file notifications. Disk write operations reuse cross-window pipe mutual exclusion automatically released upon process exit, avoiding crash-induced permanent lock files. Uninstall cancels registration, retains personal settings, and old package cache, avoiding deletion of files still referenced by other windows; currently, there is no automatic clearing of old package cache.

Windows ZIP reuses standard secure decompression implementation; plugin mode requires root manifest.json/main.js, maximum 32MiB compressed package, 128MiB expanded, 5000 entries, rejecting out-of-bound paths, links, device names, and duplicate entries. Online directories first fix GitHub commits, verify plugin id/repo/version in release packages, using limited HTTPS hosts, size, and timeout. Non-Windows installations have not been verified, and no claim is made about cross-platform installation completion.

The public constructor ABI is compatible with ES5 Parent.apply and ES class inheritance; Plugin, PluginSettings, settings items, post-processors, and others export the same core. Setting styles only affect the plugin settings window and cannot change the workbench. Failed onload and resources registered during construction are all cleaned up; post-processors disable and clear buttons and previews generated by the framework. Real plugins can freely call the host and file system; this project does not claim to be able to prevent third-party synchronization deadlocks or automatically undo any arbitrary document content modifications.

Selected real verification samples: Codeblock Copy Button 1.2.0, repository typora-community-plugin/typora-plugin-codeblock-copy-button, released ZIP SHA256 `41b52347fa526d23a5554813762309d368f440486c163c93885137229b44e704`. Additionally, there are public API fixtures covering settings saving, commands, status bar, and failure cleanup; test dummies and actual community packages are separately noted in the evidence. Plugins that depend on unopened community internal managers or another framework protocol are not within the compatibility promise.

When encountering EPERM/EACCES/EBUSY during high-frequency state writes on Windows, retry every 25ms for a maximum of 20 times during the atomic replacement phase; always retain the old configuration without deletion first. Continuously reject reporting errors to the caller and clear temporary files, keeping the original enabled state unchanged. 1000 rounds of actual temporary file system tests reproduced EPERM, and after fixing, both tiered and continuous rejection injection verification passed.

Program integrity verification uses asynchronous directory reading and streaming digest, not synchronously reading the maximum 128MiB package into the renderer; the relative path and bytes of each file are included in the same digest. During large package verification, responsiveness is restored through event loop heartbeat, but the result still needs to pass before executing the plugin.
