# Requirement Design Index and Maintenance Process

Each requirement has a stable number and a traceable design entry. Formal design is maintained with the repository version; local session logs save execution progress and evidence. Related requirements can share the same domain document, and minor fixes update the original design section, avoiding redundant maintenance of the main content. Global constraints see [AGENTS.md](../AGENTS.en.md#section_9ff23a26bc07).

<a id="section_d9308715f332"></a>
## Record and Update Process

1. When receiving feedback, first register the number, date, original intention, and acceptance conditions. Check if it supplements existing requirements; incomplete items are not covered by subsequent messages.
2. In the following table, associate authoritative design documents or sections. Before implementation, write clear plans and acceptance; if there is a document path but no detailed plan, mark it as pending design, and cannot consider functional descriptions or historical test records as the design being fully complete.
3. When there is requirement clarification, scope changes, and implementation adjustments, synchronize updates to the design content, corresponding entries, and local logs, record the date, reason, and replaced agreements. Important trade-offs retain the rationale, and the current effective plan remains unique.
4. Before completion, check each requirement, design, implementation, verification, and delivery. Verify design coverage and implementation status separately; if a parent item contains incomplete child items, retain the parent item gap.
5. When documents are moved or split, update entries and anchors. If the log is missing, first recover the number and design relationship according to this index, then verify the status according to dialogues and delivery records, without guessing the completion status.
6. As per user requirements added on 2026-09-13, after each round, submit the verified, ready-to-be-checked-in implementation, testing, design, and corresponding build, and before starting the next item, check that the previous submission is finalized. Reviewable phase implementation and platform pending acceptance items are recorded separately; after retaining clear boundaries, phase submissions can be made, not keeping a batch of verified code in an unsubmitted state for a long time, nor using submission as a substitute for complete acceptance. Only submit the content authorized and reviewed this time; changes unrelated to the user are not included.

<a id="section_1b9a96da2492"></a>
## Each single requirement design must include

- **Background and Objective**: Requirement number, source date, user original intention, current problem and expected result.
- **Scope and Acceptance**: Included and excluded behaviors, observable passing conditions, dependencies and unresolved issues.
- **Interaction and Status**: Entry, normal path, failure and cancellation behaviors; UI independent parts and cross-interface shared status.
- **Responsibilities and Approach**：Module boundaries, owners of data/configurations, command and event paths, adaptation to host or external processes; important alternative approaches and trade-offs.
- **Implementation and Verification**：Major changes, necessary impacts on configurations/data, sub-acceptance and regression methods; applicable platforms and evidence boundaries.
- **Change Records**：Dates, reasons, impact scope, and alternative relationships for requirement clarification or design changes; implementation and verification entry points are maintained in sync with changes.

Small-scale fixes can be covered in brief paragraphs under the original design section, with irrelevant items noted as not applicable and providing reasons; do not force the addition of the entire document or complex design patterns. Cross-module solutions comply with [Workbench Responsibilities and Unified Management](workspace_architecture.en.md).
