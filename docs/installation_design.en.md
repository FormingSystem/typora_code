# Installation Delivery Design

After the official host upgrade, reconnection to the enhanced subsequent architecture is seen in [R056](native_startup_design.en.md#section_f0e6be57ec2a). Currently, the following standard installation transactions are still used; automatic repair before external startup has not been implemented, and the existing workbench self-update function cannot be considered as a hook for host update completion.

<a id="section_7279525292c7"></a>
## R025

On 2026-09-13, user requirements require that readers who are first encountering Typora Code clearly understand what the product is, where to download, how to install, check, uninstall, and restore. The scope includes entry naming, environment contract, user documentation, and the actual boundaries of installation transactions; do not change the permanent startup architecture, do not release remote, and do not change user daily settings or delete user documentation.

Public entry is unified as the root directory `install_windows.ps1` / `install_windows.cmd`, `check_windows.ps1` / `uninstall_windows.ps1`, `uninstall_windows.cmd` / `restore_windows.ps1`, Bash is `install.sh`, `check.sh`, `restore.sh`. Windows transactions are assigned to `scripts/install_workspace_windows.ps1` and `scripts/restore_workspace_windows.ps1`, sharing `scripts/lib/`; UCRT64 is handed over to the same Windows transaction, and Linux calls the existing Python transaction. Old names are replaced along with the calling party, without adding duplicate aliases or repeated installation implementations.

The root README is responsible for product introduction, Windows quick start, and reading navigation; `installation.md` is the only complete user installation guide, maintaining platform, dependency, path, permission, offline cache, update, and restore processes. The old configuration guide retains the reading settings chapter and existing title anchors, and the installation part is redirected to the new guide. Historical delivery records retain the original names of the commands and note the name change relationship.

The owner of the restore state is the selected backup list. The backup restore before the first installation restores the previous environment, and the backup for subsequent installations is used for rolling back the enhanced version. It cannot be confused with uninstallation; when migrating from old plugins, the first backup may restore old plugins, so uninstalling the independent workbench does not mean deleting all third-party plugins. User settings, reading records, and non-host files are preserved. Without backup, it is not claimed that the original configuration can be restored; instead, the Typora official installer should be used to fix the host entry and retain user data.

Installation and restoration continue to execute pre-check, backup, summary verification, and failure rollback. Restoration adds host startup file comparison: after removing the entry owned by this project, if the existing files are inconsistent with the backup, it will refuse to write before writing, preventing old backups from overwriting upgrades or modified external startup pages; this is not equivalent to complete host version compatibility verification. After upgrading Typora, use the new installation and new backup. Canceling or pre-check failure does not write to the target, and installation failure uses existing transactions for rollback; do not automatically close user windows; Windows installation permission behavior is now authorized as per R063 on demand.

Acceptance covers public Windows entry points and paths with spaces, duplicate installation, damaged assets, out-of-bound backups, host change rejections, original preference restoration and subsequent preference retention, and failure rollback; Python transactions execute similar restoration boundaries. Check all current documents and scripts, help entries, build checks, and links; clearly annotate if there is no actual native verification for Linux/UCRT64/ARM64. Download instructions use the current repository web page's Code / Download ZIP, do not fabricate unverified remote project names or Release packages.

## R025 Uninstallation Entry

2026-09-14，user requested to complete the Windows double-click entry named with `uninstall`. The root directory adds `uninstall_windows.cmd` and `uninstall_windows.ps1`; CMD only passes parameters and retains the result window, PowerShell is responsible for selecting the backup for uninstall, then calls the original `restore_windows.ps1` transaction. `restore` continues to be used for explicitly selecting the backup after recovery and version rollback, without copying files for recovery, checksum verification or rollback logic.

By default, only scan the direct subdirectories of the current user's `backups/typora_code_configuration/`, read schema 4 list, user and host identity. The uninstall candidate must include the original default records of four persistent entries, the saved startup page does not contain an independent workbench entry; update backup cannot be a candidate for uninstall. The candidate also needs to pass the existing complete recovery pre-check, including source file checksum, path range and host startup page consistency. The only candidate is executed directly, multiple valid candidates are listed with time and installation location for selection; empty input cancels, cancellation and not finding valid backup do not write to the target. Custom location uses `-backup_root`, specify host uses `-typora_root`; `-non_interactive` fails when missing or ambiguous, does not wait for input, does not guess based on the latest directory.

Before execution, reject any running target Typora, prompt to save the document and exit, without closing the process or automatically elevating privileges. Display the used backup, the recovery transaction still retains the document, workbench settings and reading records; the first backup may recover the old plugin before migration. Backup discovery and target selection belong to `scripts/lib/typora_uninstall.ps1`, hosted files and native preferences recovery still belong to the existing transaction.

Acceptance covers the independent installation directory and APPDATA: only backup before installation, subsequent update backup, multiple candidates and cancellation, custom path, different users/host, missing or damaged backup, host has been updated, running process rejection, CMD parameters and exit code, as well as actual recovery after the document content, settings and reading records are kept. This time does not build or install the workbench bundle, does not uninstall the user's currently used Typora; the real uninstall of the native Windows installation location is not executed.

## R063 Windows permissions pre-check and on-demand authorization

On 2026-09-20, user requires writable installation without administrator permissions. When actual permission shortage occurs, explain and request system authorization. The existing script has no hard threshold for administrator identity, but writing to host resources/window.html may be rejected by ACL. The installation directory backup has no permission exemption, creating it may also be restricted; user data is still managed by the original account. Retain the ability to keep default user backup and -backup_root to specify a new directory, without migrating settings and running assets.

Permission service belongs to scripts/lib/typora_install_permissions.ps1, transactions still belong to the original installer. After checking the installation package and ordinary user download cache, before writing to backup and hosting, check the target write open and parent directory temporary probe. Pre-check and writing share the actual change range: if the digest is the same, the running asset does not need to be opened, and if the content of the host start page has not changed, the write permission is not detected and not covered; therefore, regular enhanced updates can maintain ordinary permissions. Only access denied into the authorization branch; read-only, file occupied, network and disk errors are separately fed back. Original files are not rewritten by the probe; subsequent race continues by the original transaction rollback.

Writable installation does not elevate privileges. Restricted installation prints specific paths, reasons for modifying the host entry, user/backup paths and cancellation semantics, and then requests system UAC again. After authorization, re-enter the same installer and re-validate. Parameter structured encoding, explicitly passing absolute host, original user data, backup, cache and theme selection, without concatenating user paths into shell code, without relying on administrator account's APPDATA. After the parent process releases the transaction lock, the child process reacquires it; the re-entry marker prevents loops. When administrator still cannot write, stop and explain, without modifying ACL.

Default interactive installation allows application; -non_interactive retains the no-person-attended semantics, can explicitly add -allow_elevation. User active installation update and UCRT64 entry explicitly pass this switch. Update progress explanation may appear system authorization; when rejected, return cancellation, installation failure retains actual logs and exit results, does not report success, does not close or restart user window. Recovery/uninstallation permission process is not within the scope of this automatic expansion.

Based on [Microsoft Start-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1) RunAs/Wait/PassThru and [UAC working principle](https://learn.microsoft.com/en-us/windows-server/security/user-account-control/how-user-account-control-works). This user authorization replaces the old installation process without applying system permission restrictions.

Verification covers PowerShell 5.1 real temporary files, ACL rejection, read-only/occupied, 20/100/1000 parameter and decision loop, simulating system authorization success/cancel/failure, temporary host installation/rollback/update and original user configuration retention. Local ordinary permission paths and asset installation checks must be executed; real secure desktop authorization and different administrator credentials not executed are explicitly retained boundaries, not replacing with stand-ins. The script is compatible with UTF-8 BOM for 5.1.

## R025 History backup and uninstall repair after host upgrade (2026-09-20)

Actual failure includes two layers: initial installation backup is schema 3, excluded by schema 4 filter; its host distribution identifier has also changed, even if version is relaxed, it cannot safely re-install original boot page. Update backup continues not to be considered as installation before environment, restore continues strict verification, not passing forged schema or ignoring host differences to bypass protection.

Default uninstall first looks for valid full installation before backup according to original contract; if exists, it uses recovery transaction and multi-candidate selection. When no candidates exist, parse the unique, full and head-located TyporaCode block in the current target installation page, only remove this entry owned by the workbench, keeping each byte (including host distribution identifier, other plugins, BOM and newline) outside the block. Four persistent assets must each appear once and all within the block; incomplete/repeated blocks, residual entries outside the range, illegal UTF-8 or host running are all rejected. Explicit-backup-root error still fails, not silently switching strategy. When no entries exist, report success as not installed, without changing files.

This path does not rehydrate the old host or recover the migrated community runtime without guessing historical preferences. Themes, framelessWindow preferences, user settings, installed community packages, and runtime resource cache are preserved; reinstallation can continue using them, and themes can be switched by the user. This belongs to the uninstallation startup integration, and it is not equivalent to clearing all data. Backups are saved to the current user's backups/typora_code_uninstall, including the original startup page and before/after summaries, transaction status; normal failures use the original backup to roll back, and logs are recorded. The pages read must be consistent with those written before; shared installations are mutually exclusive to avoid simultaneous writing with automatic updates. Atomic replacement failures do not report success.

New -check_only only reads a pre-check, outputs three plans: backup recovery / current entry removal / already uninstalled. It does not require exiting first, making it easier to locate on-site. Actual execution still requires saving and exiting, with failure logs explaining the root cause; when clear permissions are insufficient, it specifically points out the path and the reason for running the command as an administrator. Ordinary write installation does not require elevation. This item does not expand the automatic UAC scheme for recovery / uninstallation.

Acceptance covers old schema backup plus new host, only update backup, repeated execution, explicit error backup, damage marking, document content / configuration preservation, write failure rollback and concurrent changes; Windows PowerShell 5.1 real CMD runs in an isolated copy. In real environments, only read-only pre-check is done, and it is not for development acceptance uninstallation of user environments. The script is the delivery entry, and uninstall repair does not require a restart to be used; the same round of announcements are done with the 2026.09.20.17 build installation, and it cannot treat bundle installation as actual uninstallation acceptance.
