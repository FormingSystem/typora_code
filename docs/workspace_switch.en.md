# R040.1 Workspace Switching and Isolation of State

2026-09-19 User Feedback: After opening a folder or recent directory, the file tree, opened files, and Git remain in the previous directory, which may lead to accidental modification of the old project. This requirement replaces the previous design of 'mounting only the new directory and retaining the old documents'. Related to R007 File Entry, R040 Recent Directory, R027 Git Refresh, R006 Terminal, R037 Timeline and Search/Navigation.

<a id="section_aff83a42c67c"></a>
## Behavior and Boundaries

Opening a folder, recent directory, and the current window's Git working tree share the same switching process when opening and closing folders. First, validate the target, check ongoing saves, file writes, and Git write operations, then handle unsaved documents. Cancellation or save failure retains the original workspace; success closes the old editor and tool tabs, cleans up old search, navigation, fixed timeline, and Git controller. The file tree and status bar re-read from the new root directory. The terminal in the current window belongs to the old workspace, and a clear prompt is given before switching that these sessions will end. Administered windows outside of this window are not within the scope of this window.

Normal opening of files continues as file operations in the current workspace, without secretly changing the root directory to the parent directory of the file. The explicit 'open in new window' keeps the independence of the window, and the original window remains unchanged. Reopening the same directory refreshes the resources and Git, without closing the current document. The new directory starts with an empty editor area, and the user opens the target file again; this round does not add multiple root workspaces, workspace files, VS Code extension host, or a complete cross-restart layout recovery.

Unsaved documents are handled through the existing save service, allowing switching or cancellation after all documents are saved; no automatic saving, discarding, or bringing old drafts into the new workspace. This project does not have the VS Code's full hot exit backup system, so it does not silently pretend that the draft has been safely saved. Content saved to disk will not be rolled back due to later cancellation. Target validation and confirmation before closure must be completed before switching. Old read results become invalid after the workspace generation changes. Requests during switching are not executed concurrently.

<a id="section_109587d06632"></a>
## Upstream and Host Basis

Fixed VS Code 1.137.0 Commit `645f29cc3176500b4b5762ba887cf2a7f0ffdf2c`: `src/vs/platform/windows/electron-main/windowsMainService.ts`'s `shouldOpenNewWindow` reads `window.openFoldersInNewWindow` and explicit window options; `doOpenInBrowserWindow` is denied before reusing the window through `lifecycleMainService.unload(..., UnloadReason.LOAD)`, then loads the target workspace. `src/vs/workbench/services/host/electron-browser/nativeHostService.ts` hands over the folder identity to the window service. This project adopts its 'workspace switching lifecycle, protect unsaved content first' behavior, retains the existing current window/new window entry, and does not claim to read the user's VS Code private configuration.

Original Typora 1.14.10's `File.setMountFolder` only assigns the mount path, does not close tabs or publish the complete workspace lifecycle. The existing Git `context_path` prioritizes active tabs, and only subscribes to changes in active tabs, causing the root change to continue to be valid for old documents and old repositories. New common switching coordination is added, and the host still only handles native paths and recent directories; no modification to ASAR, no reinitialization of the entire workbench.

<a id="section_df53ff9b5af4"></a>
## Implementation Responsibilities and Impact

- File Service: Check all editing groups, save drafts, close confirmed safe leaves, and old open requests cannot create tabs after generation change.
- Directory Entry: System selects/path verification/serial switching/recent directory writing; target identity change is only submitted after pre-checking.
- Public Workspace Lifecycle: Unified generation, write operation denial and switching notification; shared temporary interface exit, old menus do not execute across workspaces.
- File tree/search/quick open/navigation/timeline: cancel old reads, clear old selections, fixed targets, and history jumps, and re-read new directories.
- Git: when switching, release old controllers and read tasks, and recreate the current root corresponding state; if there is no Git directory, no repository is displayed, and no old activity files are used as a fallback.
- Terminal: cancel old pending requests, end the current window old session according to confirmed switches; new sessions use new workspace root.

### R040.4 Name of the background source code tab (2026-09-23)

After the user's local restart, the previous disorder and save prompt did not reappear, but the inactive source code tab displayed internal percent-encoded paths, and clicking it restored the file name. The reason is that the title correction originally depended on the view being opened. The tab name and full path hint belong to the document identity, and do not depend on the loading of the main content; the source code view sets the name in the same way when inserting and normally opening the background tab. The background registration does not read the file, does not create Monaco, and does not change the current active item. The display uses the already parsed real file path, and no longer decodes the literal percent sign in the file name. Closing, renaming, and moving are still handled by the original resource owner. Acceptance covers the initial drawing, Chinese/blank/percent sign, long path, no editor in the background, consistent name before and after activation, and real host restart; it inherits the original tab clipping rules, and does not change the font size or width.

On 2026-09-19, the user supplemented: the previous version correctly cleared the old directory state, but after enabling the recovery configuration, re-entering the directory should continue to open the file from the last time. This section replaces the convention that 'the new root directory is always an empty editing area'; it does not change the draft protection or domain isolation.

The configuration continues to use Typora's native `restoreWhenLaunch`: in the preference settings, 2 is set to 'recover the last closed file and folder', and 0/1/3 do not automatically recover files. Each recovery reads the current native option, and does not create a synonym switch. Fixed VS Code 1.137.0 commit 645f29cc3176500b4b5762ba887cf2a7f0ffdf2c's `src/vs/workbench/browser/parts/editor/editorPart.ts` to `StorageScope.WORKSPACE` save the editing group; this time, it uses the file conversation semantics isolated by workspace, and does not transplant the complete editing group grid and hot exit backup.

The session service uniquely holds the record of opened files: using the summary of the normalized absolute root directory as an independent record key in the user data directory, Windows case and trailing separator are normalized; save the order of files, the native Markdown/source code method, fixed status, and active file. An empty editing area writes an empty list, and cannot revert to the global recent files; tools, differences, terminal, empty placeholder, and unnamed drafts are not serialized. Duplicate same file/editing method in multiple split views are deduplicated, and restored to the existing main group, without declaring the recovery of split view geometry. Files outside the directory are considered part of this session if explicitly opened by the user, and cannot be generally filtered.

Before switching, complete save/cancel pre-check, then synchronize atomic save of the old session; if persistence fails, the switch is aborted and feedback is provided. During the switch, the session sampling is paused. The old editing group is closed, and the Git/search/time line cleanup is completed before restoring the target session. R040.3 replaces the original file-by-file foreground recovery: through the common file service registration of background tabs, only one file is loaded that is allowed to be activated; missing background files are prompted when the user activates them, and are not read entirely at startup. During recovery, the switch entry is serialized; destruction cancels incomplete opens, and does not allow old recovery tasks to pollute the new workspace. The changes in open, close, and active files are debounced for persistence, and synchronized before exit; each root is independently atomic replaced, multiple windows do not overwrite other roots' records, and the last record of the same root is the standard.

Wait for the persistent module of the workbench to be ready at startup, then resume the currently mounted root; files explicitly opened by the host are prioritized as active files, and unsaved native drafts are not replaced by recovery tasks. Directories without history maintain their current files or empty state. Normal exit and re-launch use disk records; unsaved document content is not restored, and drafts are still handled by existing protection mechanisms.
