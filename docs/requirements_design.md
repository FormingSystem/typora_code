# 需求设计索引与维护流程

每条需求都有稳定编号和可追溯的设计入口。正式设计随仓库版本维护；本地会话台账保存执行进度和证据。相关需求可以共用同一领域文档，小修复更新原设计小节，避免重复维护正文。全局约束见 [AGENTS.md](../AGENTS.md#需求与设计文档管理)。

## 记录与更新流程

1. 收到反馈时先登记编号、日期、原意和验收条件，检查是否补充既有需求；未完成项不被后续消息覆盖。
2. 在下表关联权威设计文档或小节。实施前写清方案与验收；有文档路径但缺详细方案时标为待设计，不能把功能说明或历史测试记录当成设计已经充分。
3. 需求澄清、范围变化和实现调整时，同步更新设计正文、对应入口及本地台账，记录日期、原因和被替代约定。重要取舍保留理由，当前生效方案保持唯一。
4. 完成前逐项核对需求、设计、实现、验证和交付。设计覆盖与实现状态分别核对；父项包含未完成子项时保留父项缺口。
5. 文档移动或拆分时更新入口和锚点。台账缺失时，先根据本索引恢复编号及设计关系，再依据对话和交付记录核对状态，不猜测完成情况。

| 记录 | 唯一职责 |
| --- | --- |
| 本索引 | 需求编号、简要目标、权威设计入口和设计覆盖缺口 |
| 对应领域设计文档 | 需求背景、方案、交互、职责与状态、取舍及验收设计 |
| `.cache/issue_tracking/requirements.md` | 原始反馈、执行进度、待办、当次验证、提交与安装状态；不进入 Git |
| [反馈记录](feedback_review.md) | 按日期及构建保存实际验证和交付历史，不替代当前设计 |
| [设计基线](vscode_design_baseline.md) | 固定上游来源、采用值和适用边界 |

## 单条需求设计必须包含

- **背景与目标**：需求编号、来源日期、用户原意、当前问题和期望结果。
- **范围与验收**：包含与不包含的行为，可观察的通过条件，依赖和未决问题。
- **交互与状态**：入口、正常路径、失败及取消行为；UI 独立部分和跨界面共享状态。
- **职责与方案**：模块边界、数据/配置所有者、命令与事件路径、宿主或外部进程适配；重要备选方案及取舍。
- **实施与验证**：主要改动、必要的配置/数据影响、分项验收和回归方法；适用平台与证据边界。
- **变更记录**：需求澄清或设计变更的日期、原因、影响范围及替代关系；实现和验证入口随改动同步维护。

规模很小的修复可以在原设计小节中用简短段落覆盖上述要点，无关项注明不适用及理由；不强行新增整份文档或复杂设计模式。跨模块方案遵守[工作台职责与统一管理](workspace_architecture.md)。
