# 大目录搜索性能与验证

2026-09-10 的修复针对两个实际入口：顶栏／`Ctrl+P` 文件名搜索，以及侧栏内容搜索。保留原有图标、搜索范围、单击预览、双击打开和替换前预览，不改变工程文件。

## 已确认的阻塞来源

- 文件名搜索此前等全部目录枚举完才显示结果；每次输入都为全部候选创建评分对象、全量排序，再截取100项。排序比较反复传入中文区域及数字排序选项。
- 内容搜索此前逐文件等待读取与身份验证，普通文本的行索引和匹配仍在 renderer 中运行；只有正则使用 Worker。
- 侧栏先等待完整 Git 状态，再等待整轮搜索完成，最后一次性创建所有结果 DOM。引擎已有逐文件回调，但界面没有使用。

固定版本 VS Code 的 [RipgrepTextSearchEngine](https://github.com/microsoft/vscode/blob/88e44fa0e00b08f7758b4f6d05632e4fd5e4df6f/src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts) 通过独立 ripgrep 进程执行搜索、流式报告结果并在取消时终止进程；[SearchView](https://github.com/microsoft/vscode/blob/88e44fa0e00b08f7758b4f6d05632e4fd5e4df6f/src/vs/workbench/contrib/search/browser/searchView.ts) 分批更新结果树。本次采用相同的职责分离原则，继续复用工程已有的隔离 Worker 和安全替换快照，没有引入新的外部可执行文件依赖。

## 当前行为

文件名搜索最多并行枚举4个目录，发现部分文件后即可显示和打开。候选评分只维护前100项，复用一个中文数字排序器；扫描和评分按约8ms时间片主动让出 renderer。输入新查询、关闭选择器、切换工程及卸载都会使旧时间片失效；新查询尚在筛选时按 Enter，会等待该查询的结果，不能打开上次查询残留的文件。扫描最多50000个文件；状态栏明确显示仍在扫描、显示前100项或已达扫描上限，不把截断描述为全部工程已搜索。

内容搜索最多预读4个文件，保持原来的确定遍历顺序和逐文件身份检查。浏览器中，普通查询与正则均由每轮复用的一个 Worker 建立行索引、计算位置与匹配；文件系统异步读取可与此 Worker 并行。文件解码、范围规则和替换授权仍在宿主。没有匹配的文件不再预先建立完整行索引。每文件匹配超过2秒或取消时终止 Worker；超时结果保持不完整状态，不能据此执行替换。

侧栏随匹配逐文件增加结果，约80ms更新一次进度；大批量 DOM 创建每64条或约8ms让出事件循环。普通搜索的 Git 装饰与内容扫描并行；只有“仅更改文件”的搜索范围必须等待 Git 状态。`.gitignore` 所需的 Git 文件清单仍须先取得，不能为提速跳过忽略规则。新查询、停止、目录变化和卸载保留异步结果的身份隔离；未完成搜索不能预览替换。搜索、结果预览和本次性能测试均不写正文。

## 可复现基准

比较基线为 `56222589f2997a6ee2ea0a6ae87d5015f43af63b`。以下为同一台 Windows 机器的一次记录，不是跨硬件性能保证。

| 场景／指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| Chromium 中50000个文件名，完整结果可见 | 465ms | 189ms |
| 同场景，首批结果可见 | 449ms | 179ms |
| 同场景，事件循环最大计时器间隔 | 248ms | 20ms |
| 同场景，按键事件同步处理 | 69ms | 8ms |
| 1200个真实小文件，暖缓存内容扫描总耗时 | 566ms | 563ms |
| 1200个真实小文件，峰值同时读取 | 1 | 4 |
| 每次读取额外等待3ms的受控延迟场景，总耗时 | 19145ms | 4468ms |

最后一行显式插入 `setTimeout(3)`，Windows 定时器粒度会放大实际等待；它验证串行等待被有界并发重叠，不能称为真实硬盘或网络盘测量。暖缓存小文件总耗时基本持平；普通匹配进入 Worker 存在消息和线程启动成本。本次主要改善输入停顿、等待首屏结果以及高延迟读取的吞吐，不声称所有查询都按同一倍数加速。

在 `enhancements/` 执行：

```sh
node scripts/test_workspace_search_performance.mjs --baseline=56222589f2997a6ee2ea0a6ae87d5015f43af63b
node scripts/test_workspace_search_performance.mjs --baseline=56222589f2997a6ee2ea0a6ae87d5015f43af63b --read-delay=3
npx --no-install electron scripts/test_workspace_quick_open_performance.cjs --baseline=56222589f2997a6ee2ea0a6ae87d5015f43af63b
npm run check:ui -- test_workspace_files_search.cjs test_workspace_quick_open_performance.cjs
```

基线参数通过 `git show` 只读取得旧源码，构建到内存，不切换工作树或覆盖发布产物。50000个文件名使用可控制的目录接口，内容扫描使用临时真实文件；测试分别记录首结果、总耗时、事件循环间隔和读取并发，不混合为同一个指标。

## 回归与边界

目标回归覆盖真实 Worker 的正则超时／取消、普通查询进入 Worker、Unicode与多行位置、忽略规则、替换私有快照、最多4个读取并发、取消后无新读取或迟到回调，以及50000候选的最新输入胜出、筛选中按 Enter 和关闭恢复焦点。目录边界测试确保已读文件的匹配不会为填满预读队列而等待下一个慢目录。侧栏还验证慢 Git 状态和后半扫描未完成时前半结果可预览、5000条 DOM 创建中改换查询不会残留旧结果，以及列表搜索完成后保留已选结果的 DOM 节点和焦点。

默认5000条内容匹配、单文件8MiB、匹配文件快照总计64MiB的限制保持。预读内存另受并发文件数和单文件上限约束；本次没有改成无限任务队列、全工程正文缓存或持久文件索引。目录树枚举、主线程解码和最终可见节点的浏览器布局仍有成本；计时器与8ms让出点不是实时调度保证，也不代表完整移植 VS Code 搜索后端。
