# R056 直接启动工作台与宿主升级接入

2026-09-20，用户要求启动直接呈现配置后的工作台，避免原生 Typora 界面出现后再由插件覆盖；Typora 先通过官方渠道更新内核，再重新安装增强。本文为架构设计，尚未实现或验收。当前发行仍使用 [R054 首次展示控制](startup_stability.md)，不能把遮住中间画面写成已完成本需求。

同日澄清：继续使用原生 Typora 启动图标，先核对社区插件的官方更新适配。取消上一版把独立启动入口选择作为实施前置条件的安排。Typora Code 在产品性质上仍是 Typora 增强；当前直接 head 接入只是加载实现，不意味着需要另一款应用或另一个图标。

## 目标与边界

工作台成为窗口界面的呈现所有者，Typora 继续提供 Markdown 编辑、文档保存、原生对话框、窗口及官方更新能力。这里的“直接加载”是先建立最终工作台布局，再接入编辑内核和业务数据；不是取消 Typora 进程、另造 Markdown 编辑器，也不是先创建一套占位按钮，随后整体替换成真正按钮。

保留现有布局、设置、菜单和文件操作，不借启动改造增加产品功能。工作台样式属于窗口启动资源，不依赖社区插件发现或注册。工作区切换只更换业务上下文，不能重建窗口工作台。

## 已核对的调用关系

以下结论来自当前仓库代码及本机 Typora 1.14.10 的启动页面；不代表其他宿主版本兼容。

| 层次 | 当前实际入口 | 约束与变化目标 |
| --- | --- | --- |
| 宿主窗口 | `resources/window.html` | 标准安装器已在 head 中直接安装样式和常驻脚本，当前并不经过社区插件加载器 |
| 核心启动 | `enhancements/scripts/build_workspace_core.mjs` | 等待 File、editor、writingArea、sidebar-content、样式及 DOM 就绪后初始化；等待的是宿主接口，不是插件管理器 |
| 布局 | `vendor/workspace_core/src/ui/workspace.ts`、`ui/layout/workspace-root.ts`、`ui/ribbon/workspace-ribbon.ts` | 当前运行时创建工作台根和活动栏；目标改为接管启动页面中唯一的对应节点，不能再创建第二套可见布局 |
| 顶栏 | `src/workspace_titlebar.ts` | 复用窗控，但运行时组织菜单；`#title-text` 等节点仍被宿主直接访问，必须保持连接 |
| 编辑器 | `ui/editor/markdown-editor.ts` 与 Markdown 视图 | 原生编辑节点承载正文、焦点和保存状态，不能为了外观删除或重建 |
| 安装与恢复 | `scripts/install_workspace_windows.ps1`、`scripts/lib/typora_workspace.ps1`、Python 同类事务 | 安装基于当前 window.html 生成入口；恢复已拒绝以旧备份覆盖变更后的宿主页面，继续保留这条边界 |

当前加载提示与 visibility 控制只防止旧界面暴露；不减少原生初始化，也不等于上述节点已在启动页面拥有最终结构。PERF-startup-002 的未归因长任务继续独立追查。

## 启动结构与状态归属

2026-09-20实施调整：用户要求先保证现有UI、不得改动布局。实际核心在WorkspaceRoot构造、Sidebar构造和Workspace构造中分别用定时任务挂载，再由runtime轮询完成；这使节点和服务可处于不同准备阶段。第一步收敛为App完成服务创建后显式调用唯一mount：挂载原有根节点、登记原有侧栏、加载原有组件，然后才发布ready。沿用全部现有DOM工厂和CSS，不另造静态骨架；社区插件接入置于完整工作台ready之后。本阶段验证同步挂载和布局不变，不把它称为已完成模板前置接管；下文前置配置/模板方案在必要宿主API和证据明确前仍属后续设计。

安装器负责把受管理的启动资源接入宿主模板，不维护完整的 Typora 页面副本。模板改写器必须验证锚点唯一、必需原生节点存在、管理区没有歧义；未知结构在写入前失败，保留原页面。

最终布局节点由一个共享启动模块定义，构建和运行时使用同一契约。核心布局类接管已有节点，绑定结束后节点身份保持不变；不得用静态截图、复制一套菜单或每个模块各造骨架冒充最终布局。正文及宿主必需节点保持原身份，由原生适配器连接到编辑区域。需要保留但不展示的宿主菜单状态节点仍保持连接。

设置仍只有现有 Settings 所有者：布局启动读取同一份配置，并移交已解析结果，不能在 localStorage 或另一份 JSON 中复制显示设置。活动栏开关、侧栏显隐与宽度、顶栏开关、主题及缩放在第一次布局计算前生效；不能先画默认布局，再按用户设置整体跳动。

状态顺序为“启动资源和配置准备 → 建立最终布局 → 接入宿主能力 → 恢复工作区与文件 → 按模块填充异步数据”。布局节点可先存在，依赖未就绪的命令保持禁用；原生关闭、最小化和移动窗口继续有效。Git 扫描、搜索索引、语法资源不成为布局前置依赖。工作区恢复保留草稿、文件顺序和活动文件，不为缩短计时跳过恢复。

共享启动控制器拥有就绪、取消和失败状态，各模块只报告自己的接入结果。失败时撤销本次已绑定事件和宿主包装，恢复原生可操作界面并给出具体错误；不能仅去掉遮罩却留下半初始化命令。失败回退允许显示原生界面，是可见的故障处理，不属于正常启动路径。保留阶段耗时，不把等待结束时刻当作首帧时刻。

## Typora 更新与增强重新接入

官方更新器拥有 Typora 的下载、安装和版本切换。Typora Code 不修改其更新协议，也不把工作台 ZIP 当作宿主更新包。现有 R047 继续管理增强自身的版本、公告和立即安装／手动重启语义。

官方更新若覆盖window.html，增强代码不会运行。用户已于2026-09-20确认：先正常更新Typora，再从完整增强包执行现有安装和检查，手动正常重启；保持原生图标，不引入后台服务、独立启动器或自动修复。安装依赖及已验证资产沿用发行包，不要求用户拥有Git、npm或开发源码。

修复事务必须按顺序执行：

1. 解析实际宿主与用户目录，读取新版宿主身份和页面。官方更新仍在进行、路径不确定或文件不可读时暂不写入。
2. 获取标准安装互斥并重新读取身份，验证入口锚点和修复包完整性；宿主兼容性判断与“能找到 head”分开，未知版本不能自动宣称兼容。
3. 备份**升级后的**页面，再在该页面上生成增强入口；保留新版脚本、资源和编辑内核，禁止从升级前备份恢复 window.html 或 ASAR。
4. 使用标准事务写入并检查资产。失败回滚至本次修复前的新宿主状态，保留可查日志；权限不足不静默提权，不反复重试覆盖。
5. 成功后提示用户手动正常重启；失败保留具体日志，不以半安装状态显示成功。不强关既有窗口或热替换其编辑器。

本轮原始 Typora 1.14.10 隔离副本还核对了 head 时序：此时 `window.require` 已存在，`reqnode` 和 `_options` 尚未定义，不能把依赖它们的社区加载器直接搬到 head 并宣称可提前运行。现有45项启动／20轮面板切换通过，是当前基线复查，不是新启动架构验收。

## 影响评估与实施顺序

启动模块、核心容器、顶栏、设置加载、原生适配及安装事务共同受影响；文件服务、Git 服务、终端服务保留其状态所有者。在原生启动入口下实现安装模板与共享布局契约，随后迁移各容器的接管和销毁，升级后的安装流程独立接入。不能在现有延迟挂载外再叠一套“原生启动”模块形成双运行。

发布候选前必须证明配置一致、节点未替换、原生文档可保存、工作区恢复正确；不能只以加载提示消失验收。任何阶段未完成，索引、台账和公告均写明阶段状态，不增加“已支持”使用说明。
