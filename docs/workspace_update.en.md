## R047.9 Upgrade disk lifecycle (2026-09-27)

User requests for upgrades will not exhaust disks sequentially. Download completion is not transaction completion; download, unzip, install, verify, rollback, and cleanup collectively constitute one upgrade. Do not increase the size threshold for user documentation, and do not resolve space issues by clearing user backups.

| Products | Ownership and retention rules | Success, failure, and recovery behaviors |
| --- | --- | --- |
| GitHub ZIP, unzip directory | Exclusive UUID directory for update tasks; only process tasks with this product's ownership tag | Recycle upon success, download failure, validation failure, cancellation, and when the installer returns; retain if the installation or rollback sub-process is still alive |
| Crash task payload | Check registration process after the update service acquires the global update lock | Next update recycles directories older than 24 hours and where both the work process and installation/unpacking sub-processes have ended; do not delete based solely on old PID or directory age |
| Backup before original installation | Standard installer; basis for restoring native environment | Permanently retain, not included in update backup rotation |
| Automatic update rollback backup | Default backup directory; registered as automatically managed starting from this version and fully validated upgrade backup | Retain the latest one after new version installation validation passes; only then can the earlier automatically upgraded backup with the same installation/user identity be recycled |
| User-specified backup, unverified old backup, failed installation recovery site | User or original transaction | Not automatically deleted; explicitly record the reason and path when failure occurs |
| Update task status and logs | Update service | Retain the last 20 completed tasks; active and failed cleanup tasks are not affected by quantity rotation |
| Fixed Node download cache | Runtime preparation service, reusable by version and architecture | Do not repeat download/unpack for the same version; immediately clean up the .part file from this attempt; version migration and occupied runtime are handled separately |

Standard installer is responsible for backup rotation; cannot be deleted by the update UI. After successful installation, cleanup of failed tasks only reports maintenance warnings, not pretend installed versions as failed or re-rollback; retry on next successful installation. Before automatic deletion, verify fixed directory, identity, recorded file hash, complete file set, and symbolic link/junction boundaries. Retain if the directory contains additional user files; do not convert explicitly specified backup_root into automatically managed. Old version tasks without ownership markers do not guess adoption; old backups are only identified based on complete evidence of R047.11, other continue to retain.

Keep current installation if disk is insufficient or download fails; recycle this safe payload and display real errors. Wait for standard installer completion for rollback if installation has already started; do not forcefully kill the task. Backup required for restoring native environment is not cleared due to failure count. This rule applies to both manual standard installation and ZIP update, with Windows and Linux installers respectively accessing the same backup retention agreement. Untested platforms are truthfully noted.

Acceptance uses dedicated host and user directory: retain for 20 consecutive upgrades, success/failure/drop/download failure/cancel/install failure, active sub-processes and crash recovery, damaged or external link directories, original backup and user-defined directories, retain after cleanup failure and re-recycle; verify the final payload count and disk bytes, not just version number. Real network download and local ZIP transfer are separately recorded.
